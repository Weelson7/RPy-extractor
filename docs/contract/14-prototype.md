# 14. Prototype proposal (draft 2)

## 14.1 The idea in one paragraph

A **cross-platform orchestration and curation layer for game asset
extraction**. You point it at a game. It works out which engine and which
containers it's dealing with, sends each container to the best available
existing tool (with a spare if that one fails), gathers everything into one
curated workspace, and writes down where every file came from. Runtime
capture and code analysis plug into the same workspace for what static
extraction can't reach. It is **not** a new format library. The research
(doc 13) suggests the open gap is integration, safety, curation and
provenance, not parsing.

## 14.2 What changed between draft 1 and draft 2

| # | Change | Why |
|---|--------|-----|
| 1 | Unpacking is **identify, then extract** (slot `matches` becomes an Identifier with access to both the file's head *and* tail, and can carve embedded containers) | unblob's handler/extractor split; Godot PCKs embedded in executables, AGS, Love2D and NW.js all need tail access |
| 2 | New optional **CATALOG → SELECT** step before EXPORT: a plugin lists what can be extracted (heroes, maps, bundles, paks), the user or CLI picks, and only that is exported. "Dump everything" stays the default for small games | Overwatch's storage (CASC) and big Unreal games are far too large to dump in full. DataTool, AssetStudioMod and repak already filter. It could extend INVENTORY ❓ |
| 3 | **Wrapper plugins + one re-detection**: after unpacking an outer wrapper (Electron/NW.js `.asar`, `package.nw`), detection runs again on the contents | covers TyranoScript, Construct and RPG Maker MV/MZ cheaply |
| 4 | New slot family **`keys.*`** (user-supplied key first; automatic key finders only as spares) | Unreal AES, Godot encryption, Overwatch keyring |
| 5 | Every backend declares its **network use**; offline is the default | DataTool fetches a remote keyring and uses Blizzard's CDN; MelonLoader calls a remote API |
| 6 | **GPL backends are always subprocess backends** | licenses (doc 13.5) |
| 7 | **Untrusted input:** never unpickle game data in-process. Risky parsers can run isolated | Ren'Py RPA and `.rpyc` are pickles; unrpa and rpatool unpickle them unsafely |
| 8 | Runtime capture has a **hard refusal policy** and a journaled game-folder overlay | doc 11 |
| 9 | Ghidra needs **JDK 25** (12.2), not "17+"; UABEA *has* a CLI (F8 corrected) | research |

## 14.3 Prototype slices

Each slice is usable from the CLI, produces a run record, and leaves the v1
web UI working. The order goes from least risk to most.

| Slice | Content | Main / spare demonstrated | Test data |
|-------|---------|---------------------------|-----------|
| **S0 Foundation** | v1 characterization tests; `contracts`; Linux and Windows kernels; ini boot; slot binder with main/spare/promote/unbound; job runner; CLI `info`, `detect`, `extract`, `unpack`, `serve`; v1 routes as adapters | core zip/tar (stdlib) → 7z CLI; `.7z`: 7z CLI → py7zr | synthetic archives generated by the tests |
| **S1 Ren'Py** | `renpy` plugin; RPA through a **safe reader** (restricted unpickler) with unrpa as a subprocess spare; `.rpyc` → `.rpy` through unrpyc (analysis hook, optional) | safe reader → unrpa | synthetic RPA-2/3 files generated by the tests |
| **S2 Unity (port v1)** | `unity` plugin: bundles through UnityPy; `export.unity` with UnityPy as main (v1 parity) and AssetStudioModCLI as spare. The ini can swap them, which demonstrates the point of slots. Fixes F1, F3, F11 | UnityPy ↔ AssetStudioModCLI | small open-source Unity build (to find) or synthetic bundles |
| **S3 Godot** | `godot` plugin: detects PCK v1–v4, carves PCKs embedded in executables, unpacks with GDRE Tools as main and GodotPckTool as spare (unencrypted only); `keys.godot` from the user | GDRE → GodotPckTool | build a tiny PCK in a test; open-source Godot demos |
| **S4 Unreal (unpack only)** | `unreal` plugin: `.pak` via repak → QuickBMS; IoStore via retoc; `keys.unreal-aes` from the user. **Exporting assets is deferred**, because it needs our own CUE4Parse wrapper | repak → QuickBMS | sample paks built with repak itself (it can pack) |
| **S5 Custom plugin showcase: Overwatch** | an out-of-tree plugin (`plugins/overwatch/plugin.json`) wrapping DataTool (MIT, .NET 10, CI builds for win-x64 and linux-x64). Detection: `.build.info` with a `pro…` product, `data/casc/`. CATALOG through `list-heroes --json` → selection → `extract-unlocks`. Offline mode, pinned keyring. **Runtime capture refused by policy** | DataTool → CascLib (raw files only) | fake DataTool in tests; real use needs an installed game |
| **S6 Mixed mode + sanitizer phase 1** | the combination matrix (doc 3.6) over S1–S5; report-only sanitizer rules: zero-byte files, extension fixes from magic bytes, exact duplicates by hash | — | the S1–S5 fixtures |
| **S7 Runtime capture pilot** | the policy checks plus RenderDoc frame capture → texture harvest → DIFF against the static extraction, on a game we own the rights to or one that is openly licensed | RenderDoc → apitrace | open-source game |

About S5: it's the best stress test of the custom-plugin path (proprietary
engine, external .NET tool, keys, huge storage, selective extraction). But
it carries **terms-of-service exposure**: Blizzard's EULA reportedly forbids
software that "mines" game data; the current text couldn't be retrieved. It
also can't be tested with real data in CI. An alternative showcase with no
legal exposure would be an open-source game on a custom engine ❓. Your call.

## 14.4 How we'd know the prototype works

1. All 12 distro ini files boot on Linux and Windows CI runners. `rpyx info --json` shows the expected bindings.
2. The combination matrix (kernels × fixtures × plugin subsets × policies) passes.
3. Each slot passes the four main/spare cases (main up/down × spare up/down) with fake backends. Smoke tests with the real tools run where the tools are installed.
4. The v1 web UI works unchanged against the v1 characterization tests.
5. Running the same job twice from its run record gives an identical workspace (names, sizes, hashes).
6. The sandbox test shows no writes outside staging and the workspace (and, for S7, a game folder restored to identical hashes).
7. Every workspace file can be traced to its origin (game folder, archive + backend, export backend, capture).

## 14.5 Not in the prototype

UI redesign (beyond option forms rendered from plugin data, and maybe a run
history list), Wine adapters, decompiler backends beyond the hook,
sanitizer apply/transcode, Unreal asset export, additional engines (RPG
Maker, Electron/NW, GameMaker are next, doc 13.3), and third-party
vendoring beyond what S0–S3 need (doc 10's open problems come first).

## 14.6 Biggest risks

| Risk | Mitigation |
|------|-----------|
| Building on v1 semantics that are wrong (counts, layouts) | glossary first (doc 0); characterization tests before migrating; honest metrics |
| Third-party tools change or break (DataTool after every game patch, Cpp2IL pre-release) | pin versions; spares; slot self-tests (`rpyx slots --check`) |
| Legal and terms-of-service exposure | static first; capture refusal policy; offline defaults; clear user responsibility; no evasion features |
| Scope creep (it's a framework) | slices with exit criteria; each new engine is a plugin with fixtures, not a core change |
| Linux parity for Windows-only tools | prefer tools with native Linux builds (repak, retoc, GDRE, AssetStudioMod, DataTool CI); Wine is out of scope for now |
