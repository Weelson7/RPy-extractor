ViWo // Vidya Wormhole

Technical overview · version {{version}} · contract {{contract}} · {{date}}

A community-owned, local-first orchestrator for game reverse engineering. Point it at a game folder: it recognizes the engine, routes every container to the best available tool (with a spare when that tool is missing or fails), collects everything into one curated workspace and records where every file came from. From there it analyses the game's code, works with the running game, and writes changes into a patched copy. The game folder is never modified.

1 · Philosophy

  • Community tool. MIT, forkable. ViWo stays small (wiring, provenance, curation, round trip, care for the user's data); capability comes from pinned third-party tools and community data (per-game indexes and scripts).
  • For everyone who wants to look inside a game: reverse engineers, modders, artists, translators, data miners, researchers, preservationists, players, the curious. The tool judges neither the user nor the purpose.
  • No boundaries, no safeguards in the code. Nothing is refused because of what a game is, which plugin runs or what the user intends. Anti-cheat and online detection are warnings plus one opt-in (a feature switch and a confirmation), never a gate. A disclaimer replaces safeguards.
  • Borderline code is never first-party. DRM defeat, key brute force or anti-cheat evasion, if they exist, are pinned third-party tools or community scripts.
  • Engineering properties are not boundaries. Copy-not-move, traversal checks, secrets kept out of logs, a local server with a token, checksummed downloads protect the user's data and machine; any of them that blocks a wanted capability becomes an option.
  • Never silent, minimal prompts. Every fallback, empty export, skipped or unreadable file is said in the CLI and the GUI. Whatever a tool needs on first run happens by itself, off screen: no dialogs, no wizards, no installers.

2 · Architecture

A headless core with two clients (the CLI and the web UI) over three arms. A module imports only its own layer and the layers to its left; plugins never import the core or each other; the core reaches plugins, backends and the OS layer through registries filled at boot. GPL and AGPL tools run only as separate processes.

  • Survey answers first, read-only: per game or library, the engine, what each tool can open, what needs a key, dense unknown blobs.
  • Extract runs the pipeline above. An engine found inside a wrapper (an RPG Maker MV game in an Electron asar) is re-detected once inside it; its exports are derived files, never mapped back to a wrong container.
  • Keys come from the user or the game's own local files and are verified before use (an Unreal AES key on the pak index, an RPG Maker key on the images); found keys are never logged or written.
  • Curation: WORKSPACE (groups by type, trash and restore), SORT (one file at a time with previews, keep, trash, rename, undo), CLEANUP (empty, junk, mislabeled, duplicates; plan, apply, undo), MERGER (frame sequences and clips to one video).
  • Analysis of a copy: Ghidra headless and the Continue in Ghidra handoff, ilspycmd, Cpp2IL, unrpyc, GDRE Tools, unluac, Detect It Easy, Unicorn and angr on isolated routines, a function-by-function version diff. Nothing in the static arm runs the game.

4 · Slots and failover

Every format and every job is a slot with a main and an optional spare backend. A plugin declares slots and backends; the binder picks what is available on this machine.

flowchart TD
  Q[a container or a job] --> M{main available?}
  M -->|yes| RM[run the main]
  M -->|no| SP{spare available?}
  SP -->|yes| PROM[spare promoted
said in SYSTEM and slots]
  SP -->|no| UNB[unbound: the stage says
unavailable + the install hint]
  RM --> OK{outcome}
  OK -->|ok| DONE[result, notes said]
  OK -->|retryable failure| RS[run the spare
fallback said]
  OK -->|needs_key| NK[no fall-through:
the key is asked for]
  PROM --> DONE
  RS --> DONE

Every outcome carries its kind, files, error, notes and fallback. A fallback, an export that wrote nothing, and every entry an unpacker skipped (an unsafe name, a missing part file, an archive cut short) become warnings in the CLI, the GUI job log and the result.

5 · Dynamic arm: the game is running

A feature switch (capture) with warnings and one confirmation. Anti-cheat and online titles are said, never refused.

flowchart LR
  GA[(game)] --> PC[patched copy
.viwo-patched]
  PC --> AG[runtime agent
UE4SS, BepInEx]
  GA --> RD[RenderDoc capture
unattended frame]
  RD --> HV[harvest
textures, shaders]
  GA --> DU[memory dump]
  GA --> TR[Frida API trace]
  GA --> AU[sound to WAV]
  GA --> DB[x64dbg, Cheat Engine
on the game's process]
  AG --> WS[(workspace)]
  HV --> WS
  DU --> WS
  TR --> WS
  AU --> WS

Runtime agents run in a marked patched copy, never in the game folder: UE4SS writes the Unreal mappings (.usmap) that cooked UE5 assets need and an object dump; BepInEx gives Unity IL2CPP interop assemblies. A capture compares the game folder before and after and says what the game wrote there. x64dbg attaches to the game's own process (or starts its own executable), so a patch made live in the debugger lands in the real process.

6 · Patching arm: changing the content

sequenceDiagram
  participant U as User
  participant W as Workspace
  participant P as Provenance map
  participant K as Engine packer
  participant C as Patched copy
  U->>W: edits files
  W->>P: which container and member each came from
  P->>K: edited members per container
  K->>C: repacked container (an override archive where the game loads one)
  K->>C: read back and compared
  C-->>U: verified, or every member that differs named
  • Patched copy: workspace edits repacked into the game's own containers (Ren'Py RPA, Godot PCK, Unity bundles, Unreal pak, RPG Maker, Cyberpunk archives through WolvenKit).
  • Patch sets: byte patches by offset, RVA or AOB pattern, assembly through Keystone, a byte diff and an AOB export; a patch whose file the copy lacks fails alone.
  • Mods: a patched copy's changes as a mod package, checked against another game version, several applied in order.

7 · Engineering properties

  • The game folder is read-only: collect copies from it, staging is the only place files are moved from, every run compares the game folder before and after.
  • Every write into a folder built from untrusted names goes through safe_member and inside (traversal, drive letters, NTFS streams, device names, links); junctions and links in a game folder are never walked into.
  • Only folders ViWo owns are curated or cleared (a .viwo-workspace marker); a game inside its own workspace, or "replace" on a foreign folder, is refused.
  • In-process parsers of game bytes are bounded: declared sizes cap every inflate, decoders stop at their width and height, hostile-input tests feed every reader random bytes.
  • Third-party tools are pinned (version, size, sha256), HTTPS only, installed into third_party/ and nowhere else; Python packages install only from hash locks.
  • Secrets and found keys are never logged or written (run records store <secret>); tool output is masked.
  • The server binds loopback by default, answers JSON only, checks the Host header and needs a per-start token; a LAN peer gets the page only with the key link printed at start.
  • Child processes (GUI tools, launched games) are tracked and killed when ViWo exits.

8 · The web UI

Plain HTML and ES modules served by viwo serve, no build step. A functional layer (views built from a component library, talking to the API) and a style layer (CSS tokens and two themes, wormhole and plain); a lint keeps them apart and a real-browser smoke test drives every view.

  • Top bar: SYSTEM, JOBS, SETTINGS (codes 00, 01, 02), the FORMATS and JOB chips, the shared game selector and the workspace.
  • Rail: one arm at a time, STATIC, DYNAMIC, PATCHING. Each view's code is the arm's letter and its index (S0, S1, ... D0, ... P0, ...), computed at load: plugins contribute views and panels, so the numbering follows what is installed. Panels inside a view are lettered A, B, C in order.
  • Jobs: every long action is a job with live progress, a log and a result; the activity console keeps every line of every tool.

11 · Quality

  • {{test_count}} tests in layers L0 to L6: static rules (layers, caps, lint), unit and property tests (random archives, hostile input, covering designs for plugin pairs), pipeline and API tests, a real-browser UI smoke, and real-tool tests behind VIWO_L5=1.

  • Conformance: every normative item of the contract documents has a row: {{conf_implemented}} implemented, {{conf_partial}} partial, {{conf_open}} open.
  • Versioning: va.b.c; every commit runs format, lint, caps and the whole suite before it is made, and tags itself.
